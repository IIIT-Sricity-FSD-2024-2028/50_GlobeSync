## 2. Complete Endpoint Security Audit

This section audits every registered HTTP endpoint across all backend controllers. For each endpoint, three criteria are evaluated:
1. **(a) Checks Identity:** Whether the endpoint cryptographically verifies caller identity (e.g., via verified JWT signature). Currently, endpoints marked *'Header only'* merely read unverified plain-text `x-user-id` headers.
2. **(b) Checks Role:** Whether the endpoint verifies user role permissions against role metadata (`@Roles(...)`).
3. **(c) Checks Ownership:** Whether the endpoint verifies that the authenticated user owns or is assigned to the specific resource (e.g., preventing Traveler A from reading/modifying Traveler B's trips).

## 4. Architectural Summary & Remediation Recommendations

### Key Vulnerabilities Identified:
1. **Absence of Cryptographic Authentication (Zero Tokens):**
   - There are currently no JSON Web Tokens (JWT), session cookies, or cryptographic signatures implemented anywhere in the backend or frontend.
   - `auth.service.ts` directly compares plaintext strings (`password === password`) and returns the bare user object.
2. **Blind Client Header Trust (Full RBAC Bypass & IDOR):**
   - `RolesGuard` relies exclusively on caller-provided HTTP headers: `x-user-role` and `x-user-id`.
   - Any client, script, or browser tool can inject `x-user-role: superuser` and gain full administrative access over every route.
   - An attacker can inject arbitrary `x-user-id` values to read, cancel, or modify another user's private bookings, trips, and payments (Insecure Direct Object Reference).
3. **LocalStorage Used as Security Authority:**
   - The frontend `SessionContext.jsx` and `api.js` read `userRole` and `userId` directly from the browser's `localStorage` and transmit them as HTTP headers.
   - Users can escalate privileges simply by executing `localStorage.setItem('userRole', 'SUPERUSER')` in the developer console.
4. **In-Memory Volatility & Absence of Persistence:**
   - 24 in-memory array modules in `back-end/src/data/*.data.ts` hold all production state.
   - Server reboots, deployments, or multi-instance autoscaling wipe out all user changes, bookings, and ledger payments.
5. **Hardcoded Secrets & Plaintext Credentials:**
   - Administrative and user passwords (`admin123`, `super123`, `guide123`, `support123`, `agency123`, `traveler123`) are hardcoded in git version control.
   - Frontend `LoginPage.jsx` hardcodes staff secret access codes (`ADMIN-TICP`, `SUPER-2026`, etc.).
6. **Marketing Junk Data vs. Real Aggregate Stats:**
   - The public landing page (`LandingPage.jsx`) features hardcoded static numbers (`2,500+ Trips`, `150+ Guides`, `98.5% Satisfaction`) and static destination cards.
   - All internal authenticated dashboards (Traveler, Guide, Agency, Support, Admin, Superuser) dynamically calculate metrics from in-memory backend API records.

### Remediation Roadmap (For Future Implementation Phases):
1. **Database Migration:** Replace `back-end/src/data/*.data.ts` in-memory arrays with PostgreSQL relational schema managed via TypeORM or Prisma.
2. **Cryptographic Password Hashing:** Hash all user passwords using `bcrypt` (work factor 12) or Argon2id with unique salt per record.
3. **Stateless JWT Authentication:** Implement `@nestjs/jwt` and `@nestjs/passport` with `JwtStrategy` and `JwtAuthGuard`.
4. **Header Elimination:** Strip client trust for `x-user-role` and `x-user-id`; extract `req.user.id` and `req.user.role` strictly from verified JWT claims.
5. **Secret Removal:** Remove staff access codes and demo credentials from frontend code; manage production secrets via `.env` / secret managers.
